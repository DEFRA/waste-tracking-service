# Concepts

This section introduces the core concepts used throughout the Digital Waste Tracking API. It is intended for software developers, solution architects and technical stakeholders who need to understand the resource model before integrating with the service.

---

# What is a Movement?

A **Movement** represents a single waste movement being tracked through the Digital Waste Tracking Service.

A Movement is created at the start of the journey and contains the information required to describe:

- the waste
- the producer
- the carrier
- any broker or dealer
- hazardous waste information
- POPs information
- expected collection details
- expected receiving site details

When a Movement is created, the service generates a unique **Movement ID**.

Example:

```text
WM-2026-000001234
```

The Movement remains the primary record throughout the waste journey.

## Key Characteristics

- One Movement represents one waste movement.
- Every Movement has one unique Movement ID.
- A Movement can be collected.
- A Movement can be included within a Transfer.
- A Movement can be queried by a producer using Fate of Waste.

## API Endpoints

```text
POST /movements

GET /movements/{movementId}

PUT /movements/{movementId}
```

---

# What is a Movement ID?

A **Movement ID** uniquely identifies a Movement.

It is generated by the service when a Movement is created and remains unchanged throughout its lifecycle.

Example:

```text
WM-2026-000001234
```

The Movement ID is used to:

- retrieve a Movement
- update a Movement
- record collection events
- associate a Movement with a Transfer
- query Fate of Waste information

## Developer Guidance

Treat the Movement ID as:

- immutable
- globally unique
- opaque

Do not derive business meaning from the value.

---

# What is a Collection?

A **Collection** records the moment waste passes into a driver's care.

This may be:

- collection from a producer
- collection at a handover point
- transfer between drivers

Collection information typically includes:

- date and time
- collection address
- carrier details
- driver details
- actual waste observations

## Relationship to a Movement

Collections are recorded against a Movement.

```text
Movement
    │
    ▼
Collection
```

## API Endpoints

```text
POST /movements/{movementId}/collection

PUT /movements/{movementId}/collection

GET /movements/{movementId}/collection
```

---

# What is a Transfer?

A **Transfer** represents a drop-off event at a receiving site.

The Transfer links one or more Movements that are delivered together.

When a Transfer is created the service generates a unique **Transfer ID**.

Example:

```text
TR-2026-000005678
```

A Transfer acts as the handover point between the carrier and the receiver.

## Key Characteristics

- Represents a drop-off event.
- Can contain one or many Movement IDs.
- Occurs at a receiving site.
- Generates a Transfer ID.
- Becomes the parent resource for Receipt operations.

## API Endpoints

```text
POST /transfers

GET /transfers/{transferId}

PUT /transfers/{transferId}
```

---

# What is a Transfer ID?

A **Transfer ID** uniquely identifies a Transfer.

Example:

```text
TR-2026-000005678
```

Unlike a Movement ID, which identifies a waste movement, a Transfer ID identifies a delivery event.

A Transfer ID is typically communicated from the carrier to the receiving site.

The receiver uses the Transfer ID when recording receipt.

## Relationship

```text
Movement
    │
    ▼
Transfer
    │
    ▼
Receipt
```

---

# Movement ID vs Transfer ID

The most important distinction in the API is understanding the relationship between Movement IDs and Transfer IDs.

## Movement ID

Represents:

```text
A single waste movement
```

Example:

```text
WM-2026-000001234
```

Used for:

```text
Movement
Collection
Fate of Waste
```

---

## Transfer ID

Represents:

```text
A drop-off event
```

Example:

```text
TR-2026-000005678
```

Used for:

```text
Drop-off
Receipt
```

---

## Relationship Diagram

```text
WM-2026-000001234 ─┐
WM-2026-000001235 ─┼──► TR-2026-000005678
WM-2026-000001236 ─┘

                           │
                           ▼

                        Receipt
```

A Transfer can contain multiple Movement IDs.

A Movement can only have a single Movement ID.

---

# What is a Receipt?

A **Receipt** records that waste has been received by an authorised receiving site.

The Receipt is recorded by the receiver and contains:

- receipt date and time
- waste details
- carrier details
- receiver details
- treatment information
- hazardous waste information where applicable

Each Transfer can have one Receipt.

## Relationship

```text
Transfer
    │
    ▼
Receipt
```

## Preferred API Endpoints

```text
POST /transfers/{transferId}/receipt

PUT /transfers/{transferId}/receipt

GET /transfers/{transferId}/receipt
```

# Single Collection Journey

The simplest journey contains:

- one Movement
- one Collection
- one Transfer
- one Receipt

## Example

```text
Create Movement
       │
       ▼

WM-2026-000001234

       │
       ▼

Collection

       │
       ▼

Transfer
TR-2026-000005678

       │
       ▼

Receipt
```

This is expected to be the most common operational scenario.

---

# Multi-Collection Journey

Some journeys involve multiple collections before a single drop-off.

In this model:

- multiple Movements are collected
- all Movements are delivered together
- one Transfer is created

## Example

```text
Movement A
WM-2026-000001234
        │
        ▼
    Collection

Movement B
WM-2026-000001235
        │
        ▼
    Collection

Movement C
WM-2026-000001236
        │
        ▼
    Collection

        ┌────────────┐
        │ Drop-Off   │
        └─────┬──────┘
              ▼

TR-2026-000005678

              │
              ▼

           Receipt
```

The Transfer ID becomes the aggregation point linking all included Movements.

---

# Hazardous Waste Restrictions

A special business rule applies to hazardous waste.

If any Movement included in a Transfer contains hazardous waste:

```text
The Transfer must contain exactly one Movement.
```

## Allowed

```text
Transfer
└── WM-2026-000001234
```

## Not Allowed

```text
Transfer
├── WM-2026-000001234
└── WM-2026-000001235
```

when either Movement contains hazardous waste.

This rule is validated by the service when the Transfer is created.

# Fate of Waste

The Fate of Waste service provides a producer-facing view of what happened to their waste.

It provides information such as:

- collection date
- receipt date
- waste classification history
- waste mixing information
- treatment outcomes
- disposal codes
- recovery codes

## Relationship

```text
Movement
    │
    ▼
Fate of Waste
```

## Endpoint

```text
GET /movements/{movementId}/fate-of-waste
```

The producer only requires the Movement ID.

The producer does not need to know the associated Transfer ID.
